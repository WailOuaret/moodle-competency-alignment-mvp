Software is only useful if it keeps doing what it was built to do after every change. Teams therefore write automated tests next to the code. A unit test checks one small function in isolation, for example that a price calculation rounds correctly. An integration test checks that several parts work together, such as a web handler and the database behind it.

Tests run automatically each time a developer proposes a change. This practice is called continuous integration. If a test fails, the change is not merged until the problem is fixed, so the main branch always stays in a working state.

Continuous delivery extends the idea to release. A pipeline builds the program, runs the tests, packages it and deploys it to a staging environment that mirrors production. When the checks pass, the same package can be released with one action. Small, frequent releases are easier to understand and easier to roll back than rare, large ones.

After release, the team watches logs and metrics to see how the software behaves with real users. A rollback plan, such as redeploying the previous version, limits the damage when something slips through.
